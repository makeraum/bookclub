### 지역 선택 2단 구조 (시·도 → 세부 지역)
- **왜**: 참가 탭의 지역 칩이 한 줄로 길게 늘어져 있어, 지역이 늘어나면 가로 스크롤만 길어지고 사실상 못 쓰게 되므로. 지역 확장을 데이터 추가만으로 감당할 구조가 필요했음
- **무엇**:
  - `src/lib/regions.ts` 신설 — 지역 데이터를 한 파일 상수로 분리. 시·도 9개(서울/경기/인천/충남/대전/세종/충북/부산/대구) × 세부 지역 27개. 배열 순서가 칩 노출 순서이고, 지역 추가는 이 파일만 수정하면 됨
    - `RegionSelection { province, district }` — province가 null이면 전체, district가 null이면 해당 시·도 전체
    - `matchesRegion()` / `provinceOfDistrict()` / `regionSelectionLabel()` 헬퍼
  - `src/components/ui/RegionSelector.tsx` 신설 — 1단(시·도) 고르면 2단(세부 지역)이 바로 아래 줄에 펼쳐짐. 2단에도 "전체" 칩을 넣어 시·도 전체 조회 가능
    - 전체를 고르면 2단 숨김. 2단은 `max-height` + `opacity` 트랜지션(300ms)으로 부드럽게 펼침
    - 칩 줄은 가로 스크롤 가능 + `hide-scrollbar`로 스크롤바 숨김
    - 선택 토큰 기존 유지: 선택 `#1d1d1f` 배경 + 흰 텍스트 / 미선택 흰 배경 + `#d2d2d7` 보더
    - `allowAll` prop — 필터는 1단에 "전체" 노출, 모임 생성 폼은 시·도를 반드시 하나 고르게 (`allowAll={false}`)
  - `Region` 타입을 `regions.ts`의 `District`에서 파생. 목업 모임의 지역을 세부 지역 체계로 갱신(서울→강남·서초, 천안→천안 서북구/동남구)
  - 도시 커뮤니티: 신규 목록에 없는 '화성·동탄'을 '고양·일산'으로 정리. `SeojaeDashboard`의 하드코딩 지역 맵을 제거하고 `MOCK_CITY_COMMUNITIES`에서 파생
  - **남은 일**: 모임 생성 폼은 아직 앱에 없어 `RegionSelector`를 붙이지 못했음. 폼을 만들 때 `<RegionSelector allowAll={false} />`를 그대로 쓰면 됨

### 홈 탭 데모 데이터 상시 노출 (다르게 읽은 사람 · 회고 유도)
- **왜**: 두 기능이 조건부 렌더링이라 신규 계정에서는 아예 보이지 않았음. 회고 카드는 "참가했고 이미 끝난 모임"이 있어야 나오는데 목업 모임 날짜가 전부 미래라 어떤 계정에서도 뜨지 않았고, 다른 시선 카드는 sentiment 매칭이 실패하면 사라졌음. 비공개 테스트에서 테스터가 기능 자체를 못 보는 상태
- **무엇**:
  - **회고 유도 카드**: 스토리 행 바로 아래에 "지난 모임은 어땠나요? · 30초" 한 줄 카드로 항상 노출. 누르면 기존 3문항 회고 → 완료 시 "남은 문장" 카드
    - 대상 모임이 없으면 `DEMO_RETROSPECTIVE_EVENT_ID`(《싯다르타》 깊이 읽기 모임)로 폴백
    - 이미 회고를 남긴 뒤에도 카드가 사라지지 않고 "남은 문장 카드 보기"로 바뀜 → 회고 화면이 카드 단계에서 바로 열림
  - **같은 책, 다르게 읽었어요**: 《싯다르타》 밑줄 카드 **다음**에 삽입되는 독립 카드로 분리. 이전에는 이서연 카드 위에 붙어 반박 문장이 그 카드의 일부처럼 보였음
    - 구성: 제목 + 상대 이름·프로필 + 그 사람의 다른 해석 문장 1개 + "프로필 보기"
    - 매칭 실패 시 `DEMO_DIFFERENT_PERSPECTIVE`(윤채린 · 《싯다르타》 반대 시선)로 폴백 → 밑줄이 0개여도 카드는 남음
    - "프로필 보기"가 동석 기록 오버레이로 연결되도록 윤채린(`u-diff1`) 프로필 데모 데이터 추가
  - 부수 정리: 회고 대상 계산을 `useEffect` + `setState`에서 `useMemo` 파생값으로 교체(cascading render 린트 에러 제거). 회고 화면이 열린 시점의 모임 id를 스냅샷으로 고정해 제출 직후 대상이 바뀌며 화면이 흔들리는 문제 해결. 같은 모임의 "남은 문장" 카드 중복 생성 방지
- **디자인 토큰**: 기존 그대로 (surface/border/ink/sub/action, radius 18px, 카드 패딩 유지)

### 참가 탭 필터 영역 정리 (그룹 카드 + 층위)
- **왜**: 모임 분류·시도·세부지역 세 줄이 모두 같은 모양·같은 크기여서 지금 무엇을 고르는 중인지 구분이 안 됐음. 칩이 캔버스 위에 그냥 떠 있어 어느 그룹 소속인지도 불분명했고, 선택된 칩에 검정 배경과 브라우저 기본 파란 포커스 링이 겹쳐 지저분하게 보였음
- **무엇**:
  - **하나의 흰 카드로 묶음**: `#fff` + `border-radius:16px` + 기존 border 토큰. 아래 캘린더 카드와 12px 간격 유지 (캘린더 카드는 기존 18px radius 그대로 두었음 — 통일이 필요하면 한쪽을 맞추면 됨)
  - **그룹 라벨**: 첫 줄 위 "모임 종류", 둘째 줄 위 "지역" (12px / weight 600 / `#86868b` / 아래 여백 8px). 두 그룹 사이에 1px `#f5f5f7` 구분선
  - **세부 지역 층위**: 별도 라벨 없이 지역 줄 바로 아래 왼쪽 12px 들여쓰기 + `#f5f5f7` 얕은 트레이(radius 12px) 안에 담음. 칩도 한 단계 작게(13px / 6·12px, 상위는 14px / 8·16px). 시·도에서 "전체"를 고르면 트레이가 접힘 — 트레이 실제 높이를 `ResizeObserver`로 재서 `max-height` 트랜지션에 넣어 빈 여백 없이 정확히 접히게 함
  - **선택 상태 통일**: 선택 = `#1d1d1f` 배경 + 흰 텍스트 + 보더 없음(높이 정렬을 위해 투명 1px만 유지), 미선택 = 흰 배경 + `#d2d2d7` 1px + `#1d1d1f` 텍스트. 파란 아웃라인은 `.focus-ring` 클래스로 `:focus-visible`(키보드)에만 적용 — 탭 선택에는 뜨지 않음
  - **현재 선택 요약**: 카드 맨 아래 한 줄로 "경기 · 수원 · 전체 종류" 형태 표시(12px `#86868b`). 선택이 하나라도 있을 때만 오른쪽에 "초기화" 텍스트 버튼 (종류·지역만 초기화, 날짜는 캘린더 카드의 "날짜 초기화" 담당)
  - **스크롤 페이드**: 칩 줄은 가로 스크롤 유지 + 스크롤바 숨김. 오른쪽에 잘리는 칩이 있으면 배경색 그라데이션 페이드가 나타남(`ResizeObserver` + scroll 리스너로 판정). 트레이 안에서는 페이드 색을 `#f5f5f7`로 맞춤
  - `src/components/ui/FilterChips.tsx` 신설 — `FilterLabel` / `FilterDivider` / `FilterChip(size: md|sm)` / `ChipRow(fadeColor)` 공용화. `OfflineEvents`의 로컬 FilterChip 정의 제거
  - `RegionSelector`가 자체 라벨(`label` prop, 기본 "지역")과 층위 규칙을 품게 해서, 모임 생성 폼이 `<RegionSelector allowAll={false} />`를 붙이면 같은 규칙이 그대로 적용됨
  - **남은 일**: 모임 생성 폼은 여전히 앱에 없음(지역을 입력하는 폼 자체가 없음). 규칙은 `RegionSelector`에 담아뒀으니 폼을 만들 때 그대로 재사용

### 개인정보 동의 체계 구축 (개인정보보호법 대응)
- **왜**: 비공개 테스트라도 실제 이용자의 개인정보를 수집하는 이상 동의 없이 받을 수 없음. 특히 "어떤 책을 읽고 어떤 문장에 밑줄을 그었는가"는 사상·신념을 드러낼 수 있어 개인정보보호법상 민감정보에 해당하고, 취향 매칭에 쓰려면 별도 동의가 필요함. 기존 로그인 화면은 "계속하면 동의한 것으로 간주됩니다" 한 줄이 전부여서 동의로 인정받기 어려웠음
- **무엇**:
  - **회원가입 2단계화**: 이메일·비밀번호 입력 → 약관 동의 → 계정 생성. 동의를 받기 전에는 계정을 만들지 않음
    - 항목별 개별 체크박스 6개. "전체 동의"는 편의 버튼이고, 실제 동의 기준은 개별 체크 상태
    - [필수] 만 14세 이상 / 이용약관 / 개인정보 수집·이용 / 국외 이전(Supabase 일본·Vercel 미국 명시)
    - [선택] 민감정보 처리(독서기록·문장·가치관 태그) — `#f5f5f7` 회색 박스로 시각 구분 + "동의하지 않아도 가입할 수 있습니다. 취향 매칭 기능만 제한됩니다" 안내
    - [선택] 모임 알림 수신(이메일)
    - 각 항목에 "전문 보기" 아코디언. 필수 미체크 시 완료 버튼 비활성
  - **소셜 로그인·기존 계정 재동의**: `route: 'consent'` 추가. 동의 이력이 없거나 방침 버전이 올라갔으면 진입 시 동의 화면으로 보냄. 같은 `ConsentForm`을 재사용하며, 이전에 동의한 선택 항목은 체크된 상태로 시작
  - **동의 이력 저장**: `user_consents` 테이블 (user_id, consent_type, agreed, policy_version, agreed_at, ip_address)
    - **append-only 설계** — 동의도 철회도 새 행으로 쌓고 기존 행은 수정하지 않음. update·delete RLS 정책을 두지 않아 이력을 고칠 수 없게 함. "언제 무엇에 동의했고 언제 철회했는지"를 그대로 증명할 수 있음
    - 항목별 현재 상태는 `agreed_at`이 가장 최근인 행으로 판단 (`latestConsent` / `isConsentActive`)
    - IP는 `/api/client-ip`에서 `x-forwarded-for` 기준으로 받아 함께 기록. 프록시 환경에서 정확하지 않을 수 있다는 한계를 SQL 주석에 남김
  - **버전 관리**: `src/lib/consent.ts`의 `POLICY_VERSIONS` 상수를 올리면 `needsReconsent()`가 재동의를 요구. 개정 → 상수 변경 → 다음 진입 시 자동 재동의
  - **마이 → 설정 → 개인정보 관리** (`subView: 'privacySettings'`)
    - 항목별 동의 여부·동의 일시·방침 버전 조회, 개정된 항목은 "개정됨" 표시
    - 선택 동의 항목 토글로 언제든 철회 (철회도 새 행으로 기록)
    - 내 데이터 내려받기 — 프로필·밑줄·회고·남은 문장 카드·게시물·동의 이력을 JSON으로 다운로드
    - 회원 탈퇴 진입점
  - **철회하면 실제로 매칭에서 제외**: `sensitiveConsentGiven`을 기준으로 홈의 "같은 책, 다르게 읽었어요"와 서재 탭의 "추천 서재"를 안내 카드로 교체. 동의 기록 자체가 없는 상태(체험 계정·로컬 모드)에서는 기존대로 노출해 비공개 테스트 화면이 비지 않게 함
  - **회원 탈퇴**: `delete_my_account()` (security definer) 호출로 실제 삭제
    - 삭제: 밑줄·반응·회고·남은 문장 카드·동석·출석·서재 참여·밑줄 짝·초대·게이트·프로필·게시물·동의 이력·계정
    - 익명화: 피드백은 `user_id`를 null로 (서비스 개선 목적, 개인 식별 불가)
    - 보존: 내가 운영하던 서재는 주인 자리를 비우고 비활성화 — 다른 멤버들의 기록을 함께 지울 수 없기 때문. 이를 위해 `seojae.owner_id`를 null 허용 + `on delete set null`로 완화
    - 탈퇴 화면에 무엇이 삭제·익명화·보존되는지 목록으로 명시하고, "탈퇴합니다" 입력 확인을 요구
  - **/privacy, /terms 페이지**: 로그인 없이 접근 가능한 정적 페이지. 수집 항목, 민감정보 처리, 이용 목적, 보유기간, 국외 이전(Supabase 일본·Vercel 미국·알라딘 국내) 3사 표, 파기 절차, 이용자 권리, 안전성 확보 조치, 보호책임자, 권익침해 구제, 방침 변경 절차 포함. 회원가입 화면과 마이 탭 하단, 개인정보 관리 화면에서 링크
  - `.focus-ring` 유틸을 체크박스·버튼에도 적용해 키보드 접근성 유지
- **SQL**: `supabase-privacy.sql` — 다른 스키마 파일을 모두 실행한 뒤 마지막에 실행. `to_regclass` 검사를 넣어 아직 만들지 않은 테이블이 있어도 오류 없이 넘어감
- **⚠️ 배포 전 반드시 채워야 할 것**: `src/lib/policy-docs.ts`의 `OPERATOR_INFO` — 사업자명, 주소, 개인정보 보호책임자 성명, 문의 이메일. 보호책임자 성명·연락처는 개인정보처리방침의 법정 기재사항입니다

### 회비 결제 · 회계 (데모 모드)
- **왜**: 모임마다 참가비가 있는데 앱에는 금액만 적혀 있고 납부·정산은 전부 앱 밖에서 이뤄지고 있었음. 테스터 기간에는 실제 결제를 붙일 수 없으니, 계좌 이체 + 서재지기 수동 확인으로 흐름을 먼저 검증하고 나중에 PG만 갈아 끼울 수 있는 구조로 만듦
- **무엇**:
  - **참여자 — 모임 상세 "회비" 섹션**
    - 금액(12,000원 형식) · 포함 내역(공간 대여료·음료 등, 모임 유형별) · 납부 기한(모임 3일 전)
    - 내 납부 상태 3단계를 문장으로: "아직 납부하지 않았어요" / "확인 중이에요" / "9월 12일 납부 완료"
    - "회비 납부" → 결제 시트. 계좌 이체(계좌 복사 버튼 + 입금자명 안내) / 카드 / 카카오페이
    - 카드·카카오페이는 "준비 중" 배지 + 눌러도 진행되지 않고 "정식 출시 후 이용할 수 있어요" 안내
    - "이체 완료했어요" → 상태가 확인 중으로 바뀌고 서재지기 콘솔에 즉시 반영
    - 납부 완료 시 영수 카드(모임명·금액·일시·수단·확인자) 조회. 세금계산서가 아님을 명시
    - 서재지기가 정산 공개를 켜면 참가자 화면에도 수입·지출·잔액 요약이 나타남
  - **서재지기 콘솔 "회계" 탭** (발제 질문 다음)
    - 상단 요약: 걷힌 금액 · 목표 금액 · 미납 인원 — 금액과 인원 수만, 퍼센트·등급 표현 없음
    - 참가자별 목록 + 상태 필터(전체/미납/확인중/완료, 각 개수 표시)
    - '확인 중' 항목에 [입금 확인] 버튼 → 즉시 완료 처리되고 걷힌 금액에 반영
    - 미납 안내 보내기 — 문구를 미리 보여주고 발송, 발송 내역(날짜·수신자)이 남음
    - 지출 기록 추가·삭제 → 잔액 자동 계산
    - 정산 요약 공개 토글 + 참가자에게 보일 화면 미리보기

### 남은 SQL 정리 — supabase-remaining.sql
- **왜**: 스키마 파일이 12개로 늘어나면서 무엇을 실행했는지 추적이 안 됐음. 파일마다 `create table`(if not exists 없이)과 `create policy`가 섞여 있어 잘못 재실행하면 오류가 남
- **적용 여부 판단 방법**: 테이블 존재 여부를 PostgREST로 조회하면 됩니다. anon 키만으로 확인할 수 있고 데이터를 읽지 않습니다.
  ```
  curl -s -o /dev/null -w "%{http_code} 테이블명\n" \
    "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/테이블명?select=*&limit=0" \
    -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY"
  ```
  `200`이면 테이블이 있는 것(= 해당 SQL 실행됨), `404`(PGRST205 "Could not find the table")면 없는 것. RLS로 행이 안 보여도 테이블이 있으면 200이라 존재 여부 판정에 안전합니다. 파일별 대표 테이블 하나씩만 확인하면 됩니다.
- **2026-09-04 조사 결과**
  - 이미 적용: schema · highlights · gates · growth · dunbar · console · promises · feedback (8개)
  - 미적용: sentiment · retrospective · privacy · fees (4개)
  - 판정 불가: coattendance (테이블을 만들지 않고 정책만 추가하는 파일) → 안전하게 재적용 대상에 포함
- **무엇**: `supabase-remaining.sql` — 남은 것만 실행 순서대로 합친 단일 파일. 전부 재실행 안전(`create table if not exists`, 모든 `create policy` 앞에 `drop policy if exists`, `create index if not exists`, `create or replace function`)
- **덤으로 발견한 버그**: `chat_rooms` 조회가 서버에서 500으로 실패하고 있었음 — `42P17 infinite recursion detected in policy for relation "chat_members"`. `chat_members`의 SELECT 정책이 `chat_members` 자신을 조회해서 생긴 무한 재귀. `security definer` 함수 `is_chat_member()`로 재귀를 끊는 수정을 remaining 파일 6번 절에 선택 항목으로 넣어둠 (채팅 테이블은 이 저장소가 아니라 supabase-schema-chat.sql에서 만들어진 것)

### 회비 입금 계좌를 서재지기가 직접 등록
- **왜**: 입금 계좌가 `DEMO_BANK_ACCOUNT`로 하드코딩돼 있어서, 모든 모임이 같은 계좌를 보여줬음. 실제로는 모임마다 서재지기가 자기 계좌로 회비를 받으므로 그대로는 쓸 수 없었음. 계좌번호가 로그인한 누구에게나 보이는 것도 문제였음
- **무엇**
  - `DEMO_BANK_ACCOUNT` 제거. `getEventFee()`는 이제 금액·포함 내역·기한만 돌려주고 계좌는 담지 않습니다
  - `FeeAccount` 타입 신설 (은행 · 계좌번호 · 예금주 · 회비 금액 · 납부 기한). 서재지기 콘솔 → 회계 탭 맨 위에 **입금 계좌 설정** 섹션을 두고, 등록/수정 시트에서 5개 항목을 입력받습니다. 은행은 국내 21곳 목록(`BANKS`)에서 선택
  - **미설정 상태가 기본**: 계좌가 없으면 참여자 화면의 납부 버튼이 비활성되고 "서재지기가 계좌를 등록하면 납부할 수 있어요"가 뜹니다. 하드코딩을 지운 자리를 빈 값으로 두는 게 맞다고 봤습니다 — 테스터는 콘솔에서 직접 등록해 두 상태를 모두 볼 수 있습니다
  - **마스킹**: 목록·요약에는 `3333-01-****567` 형태로만 노출하고, 전체 번호 + 복사 버튼은 결제 시트에서만 보여줍니다 (`maskAccountNumber()`). 하이픈이 없는 계좌는 `1002****789` 형태
  - 서재지기가 회비를 다시 정하면 목표 금액도 그 금액 × 정원으로 다시 계산됩니다
- **DB**: `supabase-fee-accounts.sql`
  - `fees`에 `bank_name` / `account_number` / `account_holder` 정리. 기존 `bank_account` 값이 있으면 `account_number`로 옮기고 예전 컬럼을 삭제
  - **RLS를 좁혔습니다**: `fees_select`가 `using (true)`여서 계좌번호가 로그인한 누구에게나 보였습니다. 이제 **서재지기 본인 + 그 모임 참가자**만 읽습니다
  - 정책 표현식 안에서 다른 테이블을 조회하면 그 테이블의 RLS가 다시 걸려 재귀하거나 0건이 되는 문제가 있어, 판정을 `security definer` 함수 3개(`is_event_fee_host` · `is_event_participant` · `is_event_settlement_public`)로 분리하고 `fee_payments` · `expenses` 정책도 같은 기준으로 정리했습니다
  - 참고: 모임 상세에 보이는 회비 **금액**은 이 테이블이 아니라 모임 정보에서 가져오므로, 아직 참가하지 않은 사람도 금액은 그대로 볼 수 있습니다

  - 그래도 요청대로 **채팅 경로의 key를 전부 방어적으로** 바꿨습니다: 메시지 목록 `key={msg.id || \`msg-${i}\`}`, 멤버 목록 `key={m.userId || \`member-${i}\`}`, 방 목록(데모·실제) `key={room.id || \`room-${i}\`}`. 서재 상세·대시보드의 멤버 목록도 같은 폴백을 넣었습니다. 이제 id가 비어 있어도 키가 겹치지 않습니다
  - 겸사겸사 **같은 id가 두 번 그려질 수 있던 자리**도 막았습니다 — 내가 보낸 메시지가 낙관적 항목으로 이미 있는데 Realtime INSERT가 도착하면 뒤에 덧붙이지 않고 그 자리를 대체합니다 (이쪽은 키가 빈 문자열이 아니라 uuid 중복이 됩니다)
- **아직 확인하지 못한 것 — 실시간 전달**: "메시지를 보내면 상대 화면에 뜨는지"는 **현재 백엔드 상태로는 확인할 수 없습니다**. 테스트 계정으로 `chat_rooms` · `chat_members` · `chat_messages` insert가 전부 `row-level security policy` 위반으로 막힙니다. 저장소의 `supabase-schema-chat.sql`에는 "인증 사용자 누구나 방 생성" 정책이 있는데 실제 프로젝트에는 적용돼 있지 않은 것으로 보입니다. 구독이 `Subscribed to PostgreSQL`까지 가는 것은 위와 같이 확인했으니, 스키마를 적용하면 전달까지 이어질 것으로 봅니다 (적용은 운영 DB 변경이라 손대지 않았습니다)
- 참고: 함께 요청하신 `react-hooks/set-state-in-effect` 13건은 앞 커밋(`a13b554`)에서 이미 정리했고, 지금도 `eslint src` 에러 0건입니다

### 채팅 RLS 정책 정비 (supabase-schema-chat.sql)
- **왜**: 채팅 테이블에 쓰기 정책이 없어 방·멤버·메시지 insert가 전부 막혀 있었고(그래서 실시간 전달을 확인할 수 없었음), 저장소의 `supabase-schema-chat.sql`은 git에 추가조차 되지 않은 상태였음. 파일 안의 정책도 그대로 쓰기엔 느슨했습니다
- **원본에서 고친 것 3가지**
  - **무한 재귀 제거**: `chat_members`의 조회 정책이 정책 표현식 안에서 다시 `chat_members`를 조회하고 있었습니다. 이러면 그 테이블의 RLS가 다시 걸려 재귀합니다. 회비 정책(`supabase-fee-accounts.sql`)과 같은 방식으로 `is_chat_member(room_id, user_id)` **security definer** 함수로 판정을 빼고, 세 테이블의 정책이 모두 이 함수를 씁니다. 함수 실행 권한은 `authenticated`에만 부여(`anon` 회수)
  - **본인 명의 강제**: 원본 `chat_messages` insert는 "그 방 멤버이기만 하면" 통과라 `sender_id`에 남의 uuid를 넣을 수 있었습니다. `sender_id = auth.uid()` 조건을 추가하고, 없던 **삭제 정책(본인 메시지만)** 을 넣었습니다
  - **"인증 사용자 누구나 방 생성"은 유지하되 범위를 좁힘**: 모임·서재를 열 때 방이 함께 만들어져야 해서 insert는 남겼지만, `to authenticated`를 명시하고 **update·delete 정책은 두지 않았습니다** — 방 id를 선점할 수는 있어도 멤버가 아니면 읽지도 쓰지도 못하고, 남의 방 이름을 바꾸거나 지울 수도 없습니다
- **RLS 밖의 스키마 수정 1건**: `chat_rooms.type` CHECK가 `('club','event')`뿐이라 앱이 쓰는 `seojae`·`highlight_pair` 방을 만들 수 없었습니다. `ChatList`의 타입 유니온에 맞춰 넷으로 넓혔습니다 (파일 안에 따로 표시)
- **멱등**: 예전 이름 정책까지 `drop policy if exists`로 정리한 뒤 다시 만들고, `alter publication ... add table`은 `pg_publication_tables`를 확인한 뒤에만 실행합니다. 여러 번 실행해도 안전합니다
- **파일 위치**: 저장소 루트에 떠 있던 `supabase-schema-chat.sql`을 다른 `supabase-*.sql`과 같은 `withbook/`으로 옮기고 git에 추가했습니다
- **적용·확인**: 접근 가능한 자격증명이 anon 키뿐이라 DDL은 실행할 수 없습니다. Supabase SQL Editor에서 직접 실행하기로 했고, 적용 후 두 계정으로 주고받는 실시간 전달 확인이 남아 있습니다

### 채팅 RLS 적용 확인 — 두 계정 실시간 전달 성공
- **적용됨**: SQL Editor에서 `supabase-schema-chat.sql` 실행 완료. Realtime publication(4단계)도 소유자 권한 에러 없이 통과했습니다 (대시보드 Replication 수동 추가 불필요)
- **결과** (테스트 계정 A `test@withbook.kr` ↔ 새 계정 B)
  - A가 `chat:<room>` 구독 → `SUBSCRIBED` → **B가 보낸 메시지가 A에게 실시간 도착 ✅**
  - 헤드리스 크롬으로 A가 앱 화면에서 방을 열어둔 상태에서 B가 보내자 **화면에 바로 표시됨 ✅**. 반대로 A가 화면에서 보낸 것도 B에게 도착하고 자기 화면에도 표시됨 ✅. 이때 콘솔 에러 0건
  - 권한 경계: 남의 `sender_id`로 쓰기 차단(42501) ✅ / 비멤버 읽기 0건 ✅ / 비로그인 읽기 0건 ✅ / 남을 남의 방에 밀어 넣기 차단 ✅
- **정책이 맞는데도 42501이 나던 이유 — RETURNING**: 처음 확인 스크립트가 `insert(...).select().single()`로 방을 만들고 있었습니다. `chat_rooms_select`가 "그 방의 멤버만"이라, 방을 만든 직후(아직 멤버가 아닌 시점)에는 **RETURNING 행이 SELECT 정책에 걸려** `new row violates row-level security policy`가 납니다. 정책이 없어서가 아니라 **읽기 정책 때문에 나던 에러**였습니다
  - 방을 만들 때는 `.select()`를 붙이지 않고, 참여한 뒤에 읽어야 합니다. 앱의 `sendChatMessage()`는 `.select().single()`을 쓰지만 이미 멤버인 상태라 문제없습니다 (확인함)
  - 앞으로 방 생성 코드를 추가할 때 주의할 지점이라 여기 적어 둡니다
- **확인 중 발견한 것 2가지** (이번 커밋에서는 고치지 않음)
  - **방 이름이 헤더에 "채팅"으로 뜹니다**: `ChatRoomView`의 `roomName`이 `DEMO_CHAT_ROOMS` · `MOCK_SEOJAE` · `MOCK_OFFLINE_EVENTS`에서만 이름을 찾고 **DB의 `chat_rooms.name`은 보지 않습니다**. 목록에는 이름이 제대로 나오는데(그쪽은 `fetchMyChatRooms`가 DB에서 가져옴) 방 안에서만 폴백 '채팅'이 뜹니다
  - **보낸 사람이 "알 수 없음"**: Realtime 핸들러가 `users` 테이블에서 이름을 채우는데, 새로 만든 테스트 계정의 `users.name`이 비어 있어서 그렇습니다. 프로필을 설정한 계정끼리는 정상입니다
- **남은 테스트 흔적**: 메시지·멤버십은 모두 지웠고, 빈 방 행 3개(`rt-249084` · `rt-verify-288900` · `rt-ui-336119`)만 남습니다 — `chat_rooms`에 삭제 정책을 일부러 두지 않아 앱에서는 지울 수 없습니다. 대시보드 Table Editor에서 지우시면 됩니다

### 보낸 사람 "알 수 없음" 제거 — 스켈레톤 · 이전 값 유지
- **왜**: Realtime INSERT 핸들러가 메시지를 먼저 그리고 나서 `users` 테이블을 조회해 이름을 채웁니다. 그 사이가 비어 있었고, 조회가 끝나도 `users.name`이 비어 있으면 '알 수 없음'이 그대로 박혔습니다. '알 수 없음'은 사고처럼 읽혀서 브랜드 톤과도 맞지 않습니다
- **무엇** — 이름이 정해지는 순서를 세 단계로 나눴습니다
  - **도착 시점**: 같은 사람이 앞서 보낸 메시지에 이름이 이미 있으면 **그 값을 그대로 이어씁니다**(아바타도 같이). 두 번째 메시지부터는 깜빡임이 아예 없습니다
  - **아무것도 모를 때**: 빈 문자열로 두고 `OtherMessage`가 이름 자리에 **스켈레톤**을 그립니다. 높이를 잡아두어 말풍선이 밀리지 않습니다

  - `database.ts`에 `UNNAMED_READER = '독자'` 상수를 두고, 채팅 경로(`fetchChatMessages` · `fetchChatMembers`)의 `'알 수 없음'`을 이걸로 바꿨습니다. 공백만 있는 이름도 빈 값으로 봅니다(`?.trim()`)
